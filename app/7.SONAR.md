# Qualité du code : SonarQube Cloud

Le job `sonar` de la CI (`.github/workflows/ci.yml`) analyse le front avec [SonarQube Cloud](https://sonarcloud.io) : bugs, code dupliqué, code fragile (« code smells »), points sensibles de sécurité, couverture des tests. Gratuit et sans limite pour un dépôt public. Le tableau de bord d'un projet public est **public**.

## Comment c'est branché

- `npm run test:coverage` (job `test`) produit `coverage/lcov.info` (reporter `lcov` de `jest.config.ts`), transmis au job `sonar`.
- Le job `sonar` lance l'action officielle `SonarSource/sonarqube-scan-action` (épinglée sur un commit), qui lit `sonar-project.properties` à la racine : organisation, clé du projet, dossiers analysés (`app/`, sans le client Prisma généré), tests (`*.test.ts(x)`), rapport de couverture.
- Sur une PR : analyse du nouveau code et décoration de la PR par Sonar. Sur `main` : analyse de la branche principale.
- **Informatif** : `sonar` n'est pas un check exigé par le ruleset ; un échec ne bloque pas le merge. Sans le secret `SONAR_TOKEN` (PR venant d'un fork), le job ne fait rien.

## Mise en place (une fois)

1. Se connecter à [sonarcloud.io](https://sonarcloud.io) avec GitHub, **importer l'organisation GitHub** `Lanadk` (plan Free), puis **analyser le dépôt** `deputydex`.
2. Vérifier les clés dans SonarQube Cloud > projet > **Information** : `Organization Key` et `Project Key` doivent correspondre à `sonar.organization` / `sonar.projectKey` de `sonar-project.properties` (sinon, corriger le fichier).
3. **Désactiver l'analyse automatique** : projet > **Administration > Analysis Method** > décocher « Automatic Analysis ». Elle entre en conflit avec l'analyse lancée par la CI (et ne lit pas la couverture).
4. Créer un jeton : **My Account > Security > Generate Token**, puis l'ajouter au dépôt GitHub : Settings > Secrets and variables > Actions > **New repository secret** `SONAR_TOKEN`.
5. Relancer la CI (push sur une PR, ou Actions > Run workflow) : le projet se remplit dans SonarQube Cloud.

## Badges

Les badges en tête de `README.md` (Quality Gate, couverture, notes de fiabilité, sécurité, maintenabilité, duplications) viennent de SonarQube Cloud (projet > **Information** > Get project badges) et renvoient vers le tableau de bord. Ils restent vides tant que la première analyse n'a pas tourné ; ils suivent la clé `Lanadk_deputydex` (à changer avec `sonar.projectKey`).

## Lire les résultats

- **Quality Gate** : verdict global du nouveau code (couverture, duplications, problèmes). Le seuil se règle dans SonarQube Cloud, pas dans ce dépôt.
- La couverture affichée est celle de `npm run test:coverage` : mêmes fichiers que `collectCoverageFrom` de `jest.config.ts`.
- Sonar ne vérifie pas les frontières de l'architecture (domaine ↛ infrastructure, etc.) : c'est le rôle du lint (#139).
