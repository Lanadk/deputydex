# Config Driven UI

## C'est quoi ?

Le **Config Driven UI** est un pattern d'architecture frontend où le **layout et le contenu d'une page sont déclarés dans une configuration**, séparément du code de rendu.

Au lieu d'écrire du JSX directement dans chaque page, on déclare **ce qui doit s'afficher** dans un fichier de config, et un moteur de rendu générique s'occupe du reste.

```
Config (quoi afficher)  →  Renderer (comment l'afficher)  →  UI
```

---

## Le problème qu'il résout

### Sans Config Driven — approche naïve

```tsx
// page-stats.tsx
export default function StatistiquesPage() {
    return (
        <div>
            <BarChart title="Répartition par âge" data={ageData} />
            <DonutChart title="Genre" data={genreData} />
            <BarChart title="Professions" data={professionData} />
            {/* ... 20 autres charts hardcodés ... */}
        </div>
    );
}
```

**Problèmes :**
- Ajouter un chart = modifier la page
- Réutiliser un chart sur une autre page = copier-coller
- Changer l'ordre = refactorer du JSX
- 10 pages × 20 composants = 200 imports à gérer

---

## La solution — Config Driven

On sépare en quatre couches :

### 1. Le Registry — *ce qui existe*

Un registry par type de block (`chart`, `card`, `table`, `activity-calendar`), consommé via `makeRegistryHelper` (`app/(ui)/_shared/registry/registry.helper.ts`). Chaque entrée déclare la config **statique** d'affichage (titre, type de chart, colonnes de table...) — pas la donnée runtime.

```ts
// groupes/[code]/registry.ts
const GROUPE_CHART_REGISTRY: ChartConfig[] = [
    { id: "chart-deputy-parity", displayType: "donut", title: "Parité" },
    { id: "chart-groupe-professions-familles", displayType: "bar", title: "Professions" },
];

export const chart = makeRegistryHelper(GROUPE_CHART_REGISTRY, "ChartConfig");
export const card = makeRegistryHelper(GROUPES_KPI_REGISTRY, "CardConfig");
export const table = makeRegistryHelper(GROUPE_TABLE_REGISTRY, "TableConfig");
export const activityCalendar = makeRegistryHelper(GROUPES_ACTIVITY_CALENDAR, "ActivityCalendarConfig");
```

> Le registry est une **bibliothèque**. Il ne sait pas où ni comment ses entrées seront affichées, ni d'où vient la donnée.

---

### 2. La Config de page — *ce qui s'affiche et comment*

Une `PageSection[]` (voir `app/(ui)/component-library/template/sections/anchor-section/anchor.types.ts`). **Un seul `gatewayFn` par section** (pas par block) va chercher toute la donnée de la section en un appel, et la retourne sous forme de `Record<blockId, data>` — la clé doit matcher l'`id` du block/de l'entrée registry correspondante.

```ts
// groupes/[code]/config.ts
export const GROUPES_SECTIONS: PageSection[] = [
    {
        id: "groupe-composition",
        label: "Composition du groupe",
        icon: Users,
        cols: 4,
        gatewayFn: async ({ code, legislature }) => {
            const composition = await groupesGateways.getGroupeComposition(code as string, legislature as number);
            return {
                "kpi-age-average": { data: { label: "âge moyen", value: composition.groupeAverageMemberAge } },
                "chart-deputy-parity": {
                    type: "donut",
                    data: [
                        { label: "Hommes", value: composition.groupeParite.homme },
                        { label: "Femmes", value: composition.groupeParite.femme },
                    ],
                },
            };
        },
        blocks: [
            { type: "card", colSpan: 1, config: card("kpi-age-average") },
            { type: "chart", colSpan: 4, config: chart("chart-deputy-parity") },
        ],
    },
];
```

> La config déclare **quoi**, **où**, dans quel **ordre**, et **comment aller chercher la donnée** (`gatewayFn`). Pas de JSX.

---

### 3. Le Renderer — *le moteur générique*

```tsx
// block-section-renderer.tsx
export const BlockSectionRenderer = ({ block, dataMap, loading, params, actions }) => {
    switch (block.type) {
        case "chart":             return <BlockChartRenderer config={block.config} data={dataMap[block.config.id]} loading={loading} />;
        case "card":              return <BlockCardRenderer config={block.config} data={dataMap[block.config.id]} loading={loading} />;
        case "activity-calendar": return <BlockActivityCalendarRenderer config={block.config} data={dataMap[block.config.id]} loading={loading} params={params} actions={actions} />;
        case "table":             return <BlockTableRenderer config={block} data={dataMap[block.id]} loading={loading} />;
        case "paragraph":         return <BlockParagraphRenderer items={block.items} />;
    }
};
```

> Le renderer ne sait pas **ce qu'il affiche** — il sait juste **comment afficher chaque type**, en lisant la donnée déjà résolue dans `dataMap` (clé = id du block/de l'entrée registry).

---

### 4. La page — *juste une boucle*

En pratique, la page ne boucle même pas manuellement sur `gatewayFn` : elle délègue à `SectionBlockLoader`, qui appelle `useFetchSectionData(section.gatewayFn, params)` en interne et construit `dataMap`/`loading`.

```tsx
// groupe-page-client.tsx
export default function GroupePageClient({ code }: { code: string }) {
    const { legislature } = useLegislature();
    const params = useMemo(() => ({ code, legislature: legislature?.number ?? 17 }), [code, legislature]);

    return (
        <PageContentLib>
            {GROUPES_SECTIONS.map((section) => (
                <SectionBlockLoader
                    key={section.id}
                    section={section}
                    params={params}
                    onReady={() => {}}
                />
            ))}
        </PageContentLib>
    );
}
```

> La page est **vide de logique** — elle délègue tout à la config, au loader et au renderer.

## Les types de blocks disponibles

| Type                  | Contenu                                              | Composant rendu                                        |
|------------------------|--------------------------------------------------------|--------------------------------------------------------|
| `"chart"`              | `ChartConfig`                                        | `BlockChartRenderer` → `BarChartLib`, `DonutChartLib`… |
| `"card"`               | `CardConfig` (KPI, résumé...)                        | `BlockCardRenderer`                                     |
| `"activity-calendar"`  | `ActivityCalendarConfig`                             | `BlockActivityCalendarRenderer`                         |
| `"paragraph"`          | `ParagraphItem[]` (text, highlight, list, kpi)       | `BlockParagraphRenderer` → `<p/>`                       |
| `"table"`              | `TableConfig` (colonnes, filtre, pagination, export) | `BlockTableRenderer` → `TableLib`, `TableActionsLib`    |

## Ajouter un nouveau chart

**1. Ajouter au registry (config statique) :**
```ts
// groupes/[code]/registry.ts
{ id: "mon-nouveau-chart", displayType: "bar", title: "Mon chart" }
```

**2. Référencer dans les `blocks` de la section :**
```ts
// groupes/[code]/config.ts
{ type: "chart", colSpan: 2, config: chart("mon-nouveau-chart") }
```

**3. Retourner la donnée depuis le `gatewayFn` de la section, sous la même clé :**
```ts
gatewayFn: async ({ code, legislature }) => ({
    // ... autres clés de la section
    "mon-nouveau-chart": { type: "bar", data: [...] },
})
```

Zéro modification de la page ou du renderer.

---

## Ajouter un nouveau type de block

Si demain on veut un block `"map"` ou `"timeline"` :

**1. Étendre le type :**
```ts
// block-section-renderer.tsx
export type SectionBlock<TRow = unknown> =
    | { type: "chart";             ... }
    | { type: "card";              ... }
    | { type: "activity-calendar"; ... }
    | { type: "paragraph";         ... }
    | { type: "table";             ... } & TableConfig<TRow>
    | { type: "map";               ... }  // ← nouveau
```

**2. Ajouter le cas dans le renderer :**
```tsx
case "map": return <BlockMapRenderer config={block} />;
```

**3. L'utiliser dans n'importe quelle config de page.**

---

## Ce que ce n'est PAS

| Pattern | Différence |
|---------|------------|
| **Data Driven** | La config vient d'une API/BDD au runtime — modifiable sans redéploiement |
| **Hardcodé** | JSX direct dans la page — pas de séparation config/rendu |
| **Config Driven** ✓ | Config statique dans le code — typée, versionnée, scalable |

---

## Avantages

- **Scalable** — 50 pages × 30 blocks sans duplication de code
- **Typé** — TypeScript garantit que chaque block est valide à la compilation
- **Séparation des responsabilités** — données / layout / rendu sont indépendants
- **Onboarding facile** — un dev peut ajouter une section sans comprendre le renderer
- **Testable** — les `gatewayFn` sont des fonctions pures, testables unitairement

## Inconvénients

- **Overhead initial** — plus complexe à mettre en place qu'un JSX direct
- **Debugging indirect** — une erreur dans la config peut être moins lisible qu'une erreur JSX
- **Rigidité des types** — ajouter un nouveau type de block demande de modifier le type union

## Conclusion
La paresse bien placée c'est souvent le meilleur moteur de conception.
