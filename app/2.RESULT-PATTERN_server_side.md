# 📚 Result Pattern dans une architecture Clean

## 🎯 Pourquoi ?

En JavaScript, le `throw` est coûteux — il capture une stack trace à chaque fois. Sur des cas métier attendus (un acteur non trouvé, une législature absente), utiliser `throw` c'est traiter un cas normal comme une erreur technique. C'est faux sémantiquement et inutilement coûteux en mémoire.

Le Result pattern force à gérer explicitement les cas d'erreur **sans exception**.

---

## Les types

```ts
export type Success<T> = { success: true; data: T }
export type Failure<E> = { success: false; error: E }
export type Result<T, E = Error> = Success<T> | Failure<E>
```

Un `Result` est soit un succès avec une donnée, soit un échec avec une erreur typée.

---

## Les helpers disponibles

### Créer un résultat

```ts
ok(data)   // crée un Success
err(error) // crée un Failure
```

### Lire un résultat

```ts
isOk(result)   // narrowing TypeScript → accès à result.data
isErr(result)  // narrowing TypeScript → accès à result.error
```

### Extraire la valeur

```ts
// Valeur par défaut si erreur
unwrapOr(result, defaultValue)

// Fonction de fallback si erreur
unwrapOrElse(result, (error) => fallback)

// ⚠️ Throw si erreur — à utiliser avec parcimonie
// Réservé aux cas où l'échec est véritablement inattendu
unwrap(result)
```

## Les erreurs : `AppError`

`app/_shared/result-pattern/app-error.ts` définit trois erreurs, de simples littéraux string :

| Erreur | Sens | Statut HTTP |
|---|---|---|
| `NOT_FOUND` | l'entité demandée n'existe pas (groupe inconnu dans cette législature…) | 404 |
| `INVALID_INPUT` | un paramètre ne respecte pas son format (`/abc` au lieu d'un numéro de législature) | 400 |
| `DB_ERROR` | le repository a levé une exception (panne SQL, vue d'agrégation absente…) | 500 |

Chaque use-case déclare **le sous-ensemble qu'il produit réellement** : le type dit à la route ce qu'elle doit gérer.

```ts
// Un groupe peut ne pas exister → NOT_FOUND possible
Promise<Result<GroupeInfosDTO, "NOT_FOUND" | "DB_ERROR">>

// Une liste : vide = succès, seule la panne est une erreur
Promise<Result<GroupeCardDTO[], "DB_ERROR">>
```

> Migration en cours (#143) : le domaine `groupes` est migré ; les autres domaines utilisent encore `"ERROR"` (ou `"NOT_FOUND" | "ERROR"`) jusqu'à leur migration.

## Repository : il lève, le use-case convertit

Règle unique :

- Le **repository lève une exception** sur une panne technique, **en gardant la cause** :
  `throw new Error("Failed to fetch group infos", { cause: error })`.
  Il ne journalise pas : c'est fait une seule fois, dans le use-case.
- Le repository **renvoie `null` (ou une liste vide)** quand il ne trouve rien. Ce n'est pas une erreur technique.
- Le **use-case** appelle le repository via `fromRepository`, qui transforme l'exception en `err("DB_ERROR")` et la journalise (`console.error`), puis décide si `null` / vide signifie `NOT_FOUND`.

```ts
// domains/groupes/use-cases/get-groupe-infos.use-case.ts
export async function getGroupeInfosUseCase(
  repository: IGroupeInfosRepository,
  groupeCode: string,
  legislature: number
): Promise<Result<GroupeInfosDTO, "NOT_FOUND" | "DB_ERROR">> {
  const result = await fromRepository(() => repository.getGroupeInfos(groupeCode, legislature));
  if (isErr(result)) return result;           // DB_ERROR, déjà journalisée
  const entities = result.data;

  if (entities.length === 0) {
    return err("NOT_FOUND");                  // le groupe n'existe pas
  }

  const dtos = mapEntityToGroupeInfosDTO(legislature, entities);
  return ok(dtos);
}
```

Pourquoi ne pas faire renvoyer un `Result` au repository ? L'infra n'a pas à connaître les erreurs métier, et une panne SQL est vraiment exceptionnelle. Le `Result` commence au use-case, qui est la frontière du domaine.

## Route : parser, appeler, `resultToResponse`

- Les paramètres d'URL sont validés **avant** d'appeler le use-case. Ex. `parseLegislature(raw)` (`domains/legislatures/parse-legislature.ts`) renvoie `Result<number, "INVALID_INPUT">`.
- `cachedResult` (`_shared/cache/cached-response.ts`) met en cache le succès et les erreurs métier (`NOT_FOUND`), mais **jamais `DB_ERROR`** : une panne passagère ne doit pas rester servie pendant tout le TTL.
- `resultToResponse(result, messages?)` (`_shared/result-pattern/result-to-response.ts`) est le **seul endroit** où une erreur devient un statut HTTP. Succès : 200 + en-têtes de cache. Erreur : `{ error, message }` sans cache.

```ts
export async function GET(_req: Request, { params }: { params: Promise<{ code: string; legislature: string }> }) {
  const { code, legislature } = await params;
  const parsed = parseLegislature(legislature);
  if (isErr(parsed)) return resultToResponse(parsed);   // 400

  const result = await cachedResult(
    () => getGroupeInfosUseCase(prismaGroupeInfosRepository, code, parsed.data),
    ["groupe-infos", code, legislature]
  );

  return resultToResponse(result, { NOT_FOUND: "Groupe introuvable" });  // 200 / 404 / 500
}
```

Plus de `try/catch` dans la route : les pannes du repository sont déjà des `DB_ERROR`. Une exception qui s'échapperait malgré tout (bug dans un mapper) donne la 500 par défaut de Next.

---

## Où utiliser quoi

| Situation | Mécanisme |
|---|---|
| Panne technique (SQL, vue absente…) | le repository lève (`{ cause }`) → `fromRepository` → `err("DB_ERROR")` |
| Entité introuvable | le repository renvoie `null` / `[]` → le use-case renvoie `err("NOT_FOUND")` |
| Liste sans résultat | `ok([])` : ce n'est pas une erreur |
| Paramètre d'URL mal formé | `parseX(raw)` dans la route → `err("INVALID_INPUT")` |
| Erreur → statut HTTP | `resultToResponse` uniquement |
| Erreur côté front gateway | `throw new Error(...)` |
| 404 côté front gateway | `return null` |

## Référence rapide

```ts
// Créer
return ok(data);
return err("NOT_FOUND");

// Appeler un repository depuis un use-case
const result = await fromRepository(() => repository.getX(id));
if (isErr(result)) return result;
const entity = result.data;

// Répondre depuis une route
return resultToResponse(result, { NOT_FOUND: "X introuvable" });

// Lire — early return sur l'erreur
if (isErr(result)) {
  // gérer l'erreur
}
return result.data; // TypeScript sait que c'est un Success ici (pas besoin d'unwrap car narrowing)

// Valeur par défaut
const data = unwrapOr(result, []);

// Fallback
const data = unwrapOrElse(result, (error) => handleError(error));

// ⚠️ Throw — cas vraiment exceptionnel uniquement ... pas utilisé dans le codebase pour l'instant
const data = unwrap(result);
```
