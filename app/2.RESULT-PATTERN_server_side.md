# 📚 Result Pattern dans une architecture Clean

## 🎯 Pourquoi ?

En JavaScript, le `throw` est coûteux — il capture une stack trace à chaque fois. Sur des cas métier attendus (un acteur non trouvé, une législature absente), utiliser `throw` c'est traiter un cas normal comme une erreur technique. C'est faux sémantiquement et inutilement coûteux en mémoire.

Le Result pattern force à gérer explicitement les cas d'erreur **sans exception**.

---

## Les types

```ts
export type Success<T> = { success: true; data: T }
export type Failure<E> = { success: false; error: E }
export type Result<T, E = Error> = Success<T> | Failure<E>
```

Un `Result` est soit un succès avec une donnée, soit un échec avec une erreur typée.

---

## Les helpers disponibles

### Créer un résultat

```ts
ok(data)   // crée un Success
err(error) // crée un Failure
```

### Lire un résultat

```ts
isOk(result)   // narrowing TypeScript → accès à result.data
isErr(result)  // narrowing TypeScript → accès à result.error
```

### Extraire la valeur

```ts
// Valeur par défaut si erreur
unwrapOr(result, defaultValue)

// Fonction de fallback si erreur
unwrapOrElse(result, (error) => fallback)

// ⚠️ Throw si erreur — à utiliser avec parcimonie
// Réservé aux cas où l'échec est véritablement inattendu
unwrap(result)
```

## L'erreur dans ce codebase : `"ERROR"`

Contrairement à ce qu'on pourrait avoir envie de faire (un type d'erreur riche façon `{ code: "NOT_FOUND" | "DB_ERROR"; message?: string }`), la convention **réellement utilisée** dans ce repo est volontairement minimale : chaque use case retourne `Result<DTO, "ERROR">`, un simple littéral string.

```ts
// domains/groupes/use-cases/get-groupe-infos.use-case.ts

export async function getGroupeInfosUseCase(
  repository: IGroupeInfosRepository,
  groupeCode: string,
  legislature: number
): Promise<Result<GroupeInfosDTO, "ERROR">> {
  const entities = await repository.getGroupeInfos(groupeCode, legislature);

  if (!entities) {
    return err("ERROR");
  }

  const dtos = mapEntityToGroupeInfosDTO(legislature, entities);
  return ok(dtos);
}
```

La route lit `isOk`/`isErr` — pas de code d'erreur à distinguer, juste succès ou échec :

```ts
if (isOk(result)) {
  return NextResponse.json(result.data);
}

return NextResponse.json({ error: "Failed to ..." }, { status: 500 });
```

Ce n'est **pas** un pattern `AppError` riche (`NOT_FOUND` / `FORBIDDEN` / `DB_ERROR` / `VALIDATION_ERROR` distincts) — ce genre de type n'existe pas dans le codebase aujourd'hui. Si un besoin de statuts HTTP différenciés (404 vs 500) apparaît, ce serait le moment d'introduire un type d'erreur plus riche que `"ERROR"`, mais ce n'est pas fait à ce stade.

---

## Où utiliser quoi

| Situation | Mécanisme |
|---|---|
| Cas métier attendu (not found...) ou erreur technique dans le repository | `Result` + `err("ERROR")` |
| Erreur technique vraiment inattendue | `try/catch` dans la route API |
| Erreur côté front gateway | `throw new Error(...)` |
| 404 côté front gateway | `return null` |
| Cas sans erreur métier possible | `Result<T, "ERROR">` — liste vide = succès |

## Référence rapide

```ts
// Créer
return ok(data);
return err("ERROR");

// Lire — early return sur l'erreur
if (isErr(result)) {
  // gérer l'erreur
}
return result.data; // TypeScript sait que c'est un Success ici (pas besoin d'unwrap car narrowing)

// Valeur par défaut
const data = unwrapOr(result, []);

// Fallback
const data = unwrapOrElse(result, (error) => handleError(error));

// ⚠️ Throw — cas vraiment exceptionnel uniquement ... pas utilisé dans le codebase pour l'instant
const data = unwrap(result);
```
