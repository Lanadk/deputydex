# Catalogue de Statistiques

## C'est quoi ?

Le hub `/statistics` n'est pas une page-fiche comme `groupes/[code]` : c'est un
**catalogue transverse**, agrégeant des stats de 5 domaines (`acteurs`,
`groupes`, `votes`, `scrutins`, `legislatures`), dans lequel l'utilisateur
cherche, sélectionne, compare, change le format d'affichage et exporte.

Ce besoin diverge du pattern Config-Driven documenté dans
`4.CONFIG-DRIVEN_client_side.md` sur un point précis : celui-ci suppose **une
section fixe, un seul `gatewayFn`**, un `displayType` figé dans le registry.
Le catalogue a besoin de l'inverse : **une stat adressable indépendamment**,
rendue dans n'importe quel format compatible, potentiellement affichée deux
fois à la fois (comparateur). `groupes/[code]` garde son pattern actuel tel
quel — ce document décrit le second pattern, propre à `/statistics`.

## Parcours utilisateur

1. **Domaine** (`StatPicker`) : une tuile par domaine du catalogue (Députés,
   Groupes, Votes, Scrutins, Législatures).
2. **Portée** (si le domaine a un `EntityResolver`, voir plus bas) : "un
   élément précis" (`scope: "entity"`, ex. un groupe) vs "une population"
   (`scope: "aggregate"`, ex. tous les groupes), puis les contrôles propres
   au domaine (législature, recherche d'un député, liste de groupes...).
3. **Catégorie → stats** : cases à cocher, groupées par `category`. Plusieurs
   stats compatibles (même `domain` + même `scope`) peuvent être cochées à
   la fois.
4. **Comparer** (optionnel) : rejoue exactement les mêmes stats sous un
   **second contexte** (autre groupe, autre législature, autre député...) —
   pas "stat A vs stat B", mais "même stat, deux contextes". Voir
   *Le comparateur* plus bas.
5. Par stat affichée (`StatViewer`) : titre + contexte + description, format
   au choix (`SelectLib`), insight (phrase de synthèse, si dispo), chart,
   export CSV/JSON, méthodologie repliable.

## Ne pas confondre

| | `ChartConfig`/`CardConfig`/`TableConfig` | `StatDefinition` |
|---|---|---|
| Où | `groupes/[code]`, pages-fiches | `_shared/statistics/catalog/domains/<domain>/registry.ts` |
| Portée | 1 block, dans 1 section, d'1 page | Adressable depuis n'importe où (recherche, comparateur) |
| `displayType` | Figé dans le registry | Choisi à l'exécution parmi `DISPLAY_TYPE_COMPATIBILITY[dataShape]` |
| Fetch | 1 `gatewayFn` par section, toutes les clés d'un coup | 1 fetch générique par stat (`fetch-stat-data.ts`) |
| id | Unique dans son fichier | Unique dans TOUT le catalogue (`<domain>.<slug>`, via `defineStat`) |

## Le contrat `StatDefinition`

Un objet pur, sans fonction — sérialisable, donc migrable vers un catalogue
data-driven (défini en base) plus tard sans changer ce contrat :

```ts
interface StatDefinition {
    id: string;            // "<domain>.<slug>", généré par defineStat()
    slug: string;
    domain: StatDomain;    // acteurs | groupes | votes | scrutins | legislatures
    scope: StatScope;      // "aggregate" (population, éventuellement filtrée) | "entity" (un élément précis)
    title: string;
    category: string;
    keywords: string[];
    description?: string;  // "ça représente quoi", toujours visible sous le titre
    methodology: string;   // "comment c'est calculé", affiché à la demande
    dataShape: StatDataShape; // pilote le format-switcher
    unit?: string;
    populationFilters?: FilterField[]; // scope="aggregate"
    entityIdLabel?: string;            // scope="entity"
}
```

### Trois textes, trois rôles — ne pas les confondre

Une stat peut porter jusqu'à **trois** textes explicatifs, chacun avec un
rôle précis. Les confondre a déjà produit un vrai bug (une description qui
parlait d'âge sous une stat de parité, copiée-collée par erreur) :

| Champ | Rôle | Où | Statique/dynamique |
|---|---|---|---|
| `description` | "Ça représente quoi" — pour qu'un utilisateur comprenne le graphe sans réfléchir | Toujours visible, sous le titre (`StatViewer`) | Statique, écrit dans le registry |
| `methodology` | "Comment c'est calculé" — précision technique pour qui veut creuser | Replié dans `<details>` ("Comment c'est calculé ?") | Statique, écrit dans le registry |
| Insight (`INSIGHT_RESOLVERS`) | Phrase de synthèse sur LA donnée déjà chargée ("RN a un taux de femmes de 46%, au-dessus de la moyenne...") | Encart mis en avant, au-dessus du chart | Dynamique, calculé à l'exécution — voir *Insights* plus bas |

### `scope` : aggregate vs entity

- **aggregate** = stat calculée sur une population, éventuellement filtrée.
  Ex : tous les groupes, tous les scrutins d'une législature, tous les
  députés d'un groupe X.
- **entity** = stat d'un seul élément identifié par son id. Ex : un groupe,
  un scrutin, un député précis.

Le domaine, c'est **sur qui portent les chiffres** — pas ce qui filtre
l'échantillon. "Tous les députés du groupe X" reste `acteurs`/`aggregate`
(filtré par `groupeCode`), pas `groupes`/`entity`.

Le comparateur n'autorise la comparaison qu'entre deux stats de même
`domain` **et** même `scope` — voir *Le comparateur* plus bas.

### `RawStatData` : la donnée, découplée du format

```ts
type RawStatData =
    | { shape: "distribution"; items: { label: string; value: number }[] }
    | { shape: "timeseries";   points: { label: string; value: number }[] }
    | { shape: "multi-series"; series: { name: string; items: { label: string; value: number }[] }[] }
    | { shape: "points";       points: { x: number; y: number; label?: string }[] }
    | { shape: "scalar";       value: number | string; label?: string };
```

`dataShape` détermine les formats compatibles via
`DISPLAY_TYPE_COMPATIBILITY` (`_shared/statistics/data/display-type-compatibility.ts`).
Changer de format = re-choisir un `displayType` dans cette liste ; aucune
donnée à retoucher.

## Le fetch

Une seule fonction générique, `fetchStatData(definition, params)`
(`_shared/statistics/data/fetch-stat-data.ts`), appelle
`statisticsGateway.fetchStat(domain, slug, params)` →
`GET /api/statistics/[domain]/[statId]`.

Côté serveur, `route.ts` résout `(domain, statId)` via `STAT_HANDLERS`
(`api/statistics/_handlers/stat-handlers.registry.ts`), assemblé à partir
d'un fichier de handlers par domaine (`_handlers/acteurs.handlers.ts`,
`_handlers/groupes.handlers.ts`...) — registre symétrique du registre client
mais branchant use-case + repository Prisma. Ajouter une stat = une entrée
dans le handler du domaine concerné (serveur) + une entrée dans
`_shared/statistics/catalog/domains/<domain>/registry.ts` (client) — jamais
une nouvelle route.

Un handler peut aussi servir de **stat auxiliaire**, jamais proposée dans le
picker (pas d'entrée dans le registry client) mais appelable via
`statisticsGateway.fetchStat(...)` — utile pour un insight qui a besoin d'une
donnée annexe (ex : `groupes/parite-moyenne`, consommée par
`groupesPariteInsight`, voir *Insights*).

## Composants d'affichage (client)

`app/(ui)/components/statistics/` :

- **`stat-picker.tsx`** (`StatPicker`) — tuiles de domaine → `EntityResolver`
  du domaine (si dispo) → catégories/cases à cocher. Filtre en permanence via
  `getComparableStats` pour ne jamais proposer un choix domain/scope
  incompatible avec la sélection en cours.
- **`stat-viewer.tsx`** (`StatViewer`) — l'unité atomique : fetch
  (`useStatData`), libellé de contexte (`buildContextLabel`), description,
  insight (`useStatInsight`), format-switcher, chart (`RenderStatChart`),
  export CSV/JSON, méthodologie repliable. Instancié une fois par (stat
  sélectionnée × contexte) — identique en exploration (1 contexte) et en
  comparaison (2 contextes), aucune prop ne diverge entre les deux.
- **`render-stat-chart.tsx`** (`RenderStatChart`) — bascule `RawStatData` +
  `displayType` vers le composant chart concret (`BarChartLib`,
  `PieChartLib`, `KpiCardLib`...). Le pendant, pour le catalogue, de
  `BlockChartRenderer` (config-driven sections) — mêmes composants chart,
  entrée différente.

## Le comparateur

État géré par `ComparatorProvider` (`app/(ui)/providers/comparator-provider.tsx`,
React context) + `comparatorReducer` (`_shared/statistics/comparator/comparator.reducer.ts`) :

```ts
interface ComparatorState {
    mode: "single" | "split";
    selectedStatIds: string[];               // toutes même domain + scope (garanti par le reducer)
    contexts: StatFetchParams[];              // length 1 en single, 2 en split
    displayTypes: Record<string, ChartDisplayType>[]; // displayTypes[contextIndex][definitionId]
}
```

Le comparateur ne compare pas "stat A vs stat B" mais **le même ensemble de
stats rejoué sous 1 ou 2 contextes** (groupe X vs groupe Y, législature 16 vs
17, député A vs député B...). `ENABLE_SPLIT` clone le format d'affichage
(comparer un bar à un donut par défaut n'aurait pas de sens) mais **jamais le
contexte** — le contexte B démarre vide, sinon les deux colonnes afficheraient
la même donnée tant que l'utilisateur n'a rien changé.

`buildContextLabel(domain, context, fallback)`
(`_shared/statistics/context/build-context-label.ts`) transforme un
`StatFetchParams` en libellé humain ("RN — 17ᵉ législature", "Amélie
Durand", "Tous les groupes — 16ᵉ législature") — utilisé à la fois par
`StatViewer` (badge sous CHAQUE carte, exploration et comparaison confondues)
et par le hub (en-tête "Contexte A/B" au-dessus de la grille, en comparaison
seulement).

`isContextReady(domain, scope, context)` (`_shared/statistics/context/is-context-ready.ts`)
est la source de vérité unique pour "ce contexte a-t-il tout ce qu'il faut" —
utilisée pour ne pas afficher les catégories du picker trop tôt, et pour ne
pas fetcher un `StatViewer` avec des paramètres incomplets.

## `EntityResolver` : "quel élément précis, quelle population ?"

Un domaine qui propose un choix "entité précise vs population" AVANT les
catégories (`app/(ui)/components/statistics/entity-resolvers/<domaine>/`)
s'enregistre dans `ENTITY_RESOLVERS`
(`entity-resolvers/entity-resolvers.registry.ts`) :

```ts
export const ENTITY_RESOLVERS: Partial<Record<StatDomain, EntityResolver>> = {
    groupes: GroupeEntityResolver,
    acteurs: ActeurEntityResolver,
};
```

Un domaine absent de ce registre (`votes`, `scrutins`, `legislatures`
aujourd'hui) saute directement aux catégories — toutes ses stats sont
`aggregate` sans entité à choisir, et `isContextReady` renvoie toujours
`true` pour lui.

Contrat (`entity-resolver.types.ts`) :

```ts
interface EntityResolverProps {
    value: StatFetchParams;            // contexte en cours d'édition, CE côté
    scope: StatScope;
    onChange: (scope: StatScope, params: StatFetchParams) => void;
    lockedScope?: StatScope | null;    // bride le toggle entity/aggregate en comparaison
    otherContext?: StatFetchParams | null; // contexte de L'AUTRE côté, pour griser "comparer à soi-même"
}
```

### Griser "comparer à soi-même" — piège à connaître

`otherContext` sert à rendre **impossible** une comparaison qui n'aurait pas
de sens, plutôt que de la corriger après coup. Deux règles distinctes, à ne
pas mélanger (un bug réel est passé par là) :

1. **La législature entière** ne doit être grisée pour l'autre contexte
   **qu'en scope `aggregate`** — comparer "tous les groupes de la 17ᵉ" à
   "tous les groupes de la 17ᵉ" compare une population à elle-même. En scope
   `entity`, les DEUX législatures doivent rester sélectionnables des deux
   côtés : "groupe X (17ᵉ) vs groupe Y (17ᵉ)" est une comparaison
   parfaitement valide.
2. **L'entité précise** ne doit être grisée en face que si elle désigne
   vraiment la même chose — id **ET** législature identiques. Un id peut être
   réutilisé d'une législature à l'autre pour "le même" groupe politique (ex:
   le code `HOR` existe en 16ᵉ et en 17ᵉ législature) : comparer HOR-16 à
   HOR-17 est une comparaison temporelle légitime et doit rester possible.
   Griser sur le seul id la bloquerait à tort — voir
   `groupe-entity-resolver.tsx`, `disabled={groupe.code === otherEntityId && selectedLegislature === otherLegislature}`.

En clair : la contrainte "pas de comparaison avec soi-même" se pose toujours
sur **l'identifiant complet d'une population** (entité + législature en scope
entity ; législature seule en scope aggregate), jamais sur un seul de ses
morceaux pris isolément.

### `FilterGroupLib` : labelliser un groupe de contrôles

`app/(ui)/component-library/molecules/filter-group/filter-group-lib.tsx` —
molécule générique : un label au-dessus d'une rangée de contrôles (boutons,
select...), avec séparation visuelle claire entre groupes voisins. À utiliser
dans tout `EntityResolver` (et ailleurs) dès qu'une rangée de boutons ne dit
pas d'elle-même ce qu'elle filtre :

```tsx
<FilterGroupLib label="Législature">
  <ButtonLib text="17ᵉ législature" size="small" variant="primary" onClick={...} />
  <ButtonLib text="16ᵉ législature" size="small" variant="tertiary" onClick={...} />
</FilterGroupLib>
```

Démo : `/component-library/molecules/filter-group`.

## Insights : phrase de synthèse

`app/(ui)/_shared/statistics/insights/` — un `InsightResolver` optionnel par
stat (clé = `StatDefinition.id`, pas la forme de donnée : savoir QUOI
comparer — "la législature précédente", "la moyenne du domaine"... —
dépend du sens métier de la stat) :

```ts
type InsightResolver = (
    definition: StatDefinition,
    context: StatFetchParams,
    current: RawStatData
) => Promise<string | null>;
```

Enregistré dans `insight-resolvers.registry.ts` :

```ts
export const INSIGHT_RESOLVERS: Partial<Record<string, InsightResolver>> = {
    "groupes.parite": groupesPariteInsight,
};
```

`useStatInsight` (`insights/use-stat-insight.ts`) l'appelle une fois la
donnée chargée, et n'affiche l'encart que si le resolver renvoie un texte
non-`null`. Règle stricte : **jamais de phrase à moitié vide**. Un resolver
tente ses comparaisons (ex: `Promise.all` sur "législature précédente" et
"moyenne du domaine" dans `groupes-parite.insight.ts`), assemble les clauses
qui ont réussi, et renvoie `null` si aucune n'a abouti — plutôt qu'une phrase
tronquée ou générique.

## Où vivent les fichiers

Toute la logique (types, catalogue, comparateur, hooks) est du code
présentation transverse, pas du domaine hexagonal (`app/domains/`) : rien
ici n'est backé par un repository Prisma propre — chaque stat délègue au
use-case du VRAI domaine concerné (voir `route.ts`). Elle vit donc sous
`app/(ui)/_shared/statistics/`, aux côtés des autres helpers transverses de
l'UI (`app/(ui)/_shared/adapter/`, `app/(ui)/_shared/registry/`) :

```
app/(ui)/
  _shared/statistics/
    catalog/        // types + agrégation transverse (STATS_CATALOG)
      domains/
        acteurs/registry.ts
        groupes/registry.ts       // TODO : backend existant, à exposer
        legislatures/registry.ts  // TODO : backend existant, à exposer
        votes/registry.ts         // vide : pas de backend
        scrutins/registry.ts      // vide : pas de backend
    comparator/     // état du comparateur (reducer + types) — provider à part, voir plus bas
    context/        // "ce contexte est-il prêt/vide ?" + libellé de contexte (build-context-label.ts)
    data/           // fetch générique + format d'affichage + export
    insights/       // phrases de synthèse générées par stat (InsightResolver + registry)
  components/statistics/
    stat-picker.tsx, stat-viewer.tsx, render-stat-chart.tsx
    entity-resolvers/
      entity-resolvers.registry.ts, entity-resolver.types.ts
      groupes/groupe-entity-resolver.tsx, acteurs/acteur-entity-resolver.tsx
  component-library/molecules/filter-group/   // FilterGroupLib, réutilisé par les EntityResolvers
  providers/
    comparator-provider.tsx   // React context, aux côtés des autres providers de l'app
  (views)/(db)/statistics/
    page.tsx, statistics-page-client.tsx   // la vue seule : orchestre picker + viewer

app/api/statistics/
  [domain]/[statId]/
    route.ts               // composition root HTTP : parsing + cache + dispatch, rien d'autre
  _handlers/
    stat-handler.types.ts
    acteurs.handlers.ts, groupes.handlers.ts, votes.handlers.ts,
    scrutins.handlers.ts, legislatures.handlers.ts   // 1 fichier par domaine : use-case + repository Prisma
    stat-handlers.registry.ts   // assemble les 5 fichiers ci-dessus ; seul import de route.ts
```

`STATS_CATALOG` (`_shared/statistics/catalog/stats-catalog.ts`) est le seul
point d'entrée pour parcourir "toutes les stats" côté client — jamais
d'import direct d'un registry de domaine ailleurs dans l'app. Côté serveur,
`STAT_HANDLERS` (`api/statistics/_handlers/stat-handlers.registry.ts`) joue
le même rôle : seul `route.ts` l'importe, jamais un fichier de handlers de
domaine directement.

## Comment ajouter une nouvelle stat (domaine existant)

Le domaine a déjà un backend (`acteurs`, `groupes` aujourd'hui) et,
éventuellement, un `EntityResolver` :

1. **Repository/use-case** (`app/domains/<domain>/`, `app/infrastructure/<domain>/`)
   — s'ils n'existent pas encore pour cette donnée, les créer en suivant
   `1.CLEAN-ARCHI_server_side.md`. Le use-case renvoie un `Result<DTO, "ERROR">`.
2. **Handler serveur** — dans `app/api/statistics/_handlers/<domain>.handlers.ts`,
   une entrée qui appelle le use-case et mappe le DTO vers `RawStatData` :
   ```ts
   "mon-slug": async (params) => {
       const result = await getMaStatUseCase(monRepository, params.filters?.legislature as number | undefined);
       if (!isOk(result)) return null;
       return { shape: "distribution", items: result.data.items };
   },
   ```
   Rien à toucher dans `route.ts` ni dans `stat-handlers.registry.ts` — le
   fichier du domaine y est déjà assemblé.
3. **`StatDefinition` client** — dans
   `_shared/statistics/catalog/domains/<domain>/registry.ts` :
   ```ts
   defineStat("<domain>", "mon-slug", {
       scope: "aggregate" | "entity",
       title: "...",
       category: "...",
       keywords: [...],
       description: "Ce que ça représente, en langage clair.",
       methodology: "Comment c'est calculé, techniquement.",
       dataShape: "distribution" | "timeseries" | "multi-series" | "points" | "scalar",
       unit: "...",
   }),
   ```
   `slug` doit être identique des deux côtés (client et handler) — c'est ce
   qui les relie, pas un id partagé en dur.
4. **Insight** (optionnel) — si une phrase de synthèse a du sens pour cette
   stat, ajouter un `InsightResolver` (`insights/<xxx>.insight.ts`) et
   l'enregistrer dans `INSIGHT_RESOLVERS` sous `"<domain>.mon-slug"`.
5. **Vérifier** : `npm run dev`, sélectionner la stat dans `/statistics`,
   confirmer chart + export + méthodologie + (si ajouté) insight.

## Comment ajouter un nouveau domaine

Plus rare — `votes`/`scrutins`/`legislatures` ont déjà leur registry (vide
ou partiel) et sont déjà dans `STATS_CATALOG`/`STAT_HANDLERS`, donc souvent
il ne s'agit que d'y ajouter des stats (section précédente). Pour un domaine
entièrement nouveau :

1. Ajouter la valeur à `StatDomain` (`app/_shared/statistics/stat-scope.types.ts`).
2. Créer `_handlers/<domain>.handlers.ts` (peut démarrer vide, `{}`) et
   l'assembler dans `stat-handlers.registry.ts`.
3. Créer `_shared/statistics/catalog/domains/<domain>/registry.ts` (peut
   démarrer vide, `[]`) et l'assembler dans `stats-catalog.ts`, avec une
   icône (`StatDomainModule.icon`).
4. **Si** le domaine a un vrai choix "entité précise vs population" (comme
   `groupes`/`acteurs`) : créer `entity-resolvers/<domain>/<domain>-entity-resolver.tsx`
   (voir *EntityResolver* plus haut — attention en particulier à la règle
   "griser comparer à soi-même"), et l'enregistrer dans `ENTITY_RESOLVERS`.
   Sinon, ne rien faire : `isContextReady` et `StatPicker` traitent déjà
   l'absence de resolver comme "toutes les stats sont aggregate, jamais de
   filtre à choisir avant les catégories".
5. Ajouter les stats du domaine (section précédente).
