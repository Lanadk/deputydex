# Stratégie API & Cache

## Le mécanisme réel : `unstable_cache` côté route handler

Les gateways front (`app/(ui)/gateways/**`) font des `fetch` simples, **sans** option `next: { revalidate }` ni `next: { tags }` — le cache ne se joue pas là.

Le cache est appliqué **côté serveur, dans le Route Handler**, via deux helpers dans `app/_shared/cache/` :

```ts
// app/_shared/cache/cached-response.ts
import { unstable_cache } from "next/cache";

export function cachedRead<T>(
    fn: () => Promise<T>,
    keyParts: string[],
    extraTags: string[] = []
): Promise<T> {
    if (ACTIVE_CACHE_TTL_SECONDS === CACHE_TTL_SECONDS.NO_CACHE) {
        return fn(); // pas de cache : appel direct
    }

    return unstable_cache(fn, keyParts, {
        revalidate: ACTIVE_CACHE_TTL_SECONDS,
        tags: [PARLIAMENT_DATA_CACHE_TAG, ...extraTags],
    })();
}

export function cachedJson<T>(data: T, status = 200): NextResponse {
    return NextResponse.json(data, {
        status,
        headers: {
            "Cache-Control": `public, s-maxage=${ACTIVE_CACHE_TTL_SECONDS}, stale-while-revalidate=86400`,
        },
    });
}
```

Pourquoi côté route et pas côté `fetch()` client : `fetch(url, { next: { revalidate } })` ne fonctionne que pour du fetch fait depuis un Server Component. Les gateways de ce projet sont appelées depuis des **composants client** — `unstable_cache` dans le Route Handler fonctionne quel que soit l'appelant.

`keyParts` doit inclure l'identifiant de l'endpoint + tous les paramètres qui font varier le résultat (id, code, législature...), sinon deux requêtes différentes partagent la même entrée de cache.

### Use-case qui renvoie un `Result` : `cachedResult`

`cachedRead` met en cache **tout** ce que renvoie `fn`, y compris un `Result` en échec : une panne passagère de la base resterait alors servie pendant tout le TTL. Toutes les routes, dont les use-cases renvoient un `Result` (voir `2.RESULT-PATTERN_server_side.md`), utilisent donc `cachedResult`, qui s'appuie sur `cachedRead` :

```ts
const result = await cachedResult(
    () => getGroupeInfosUseCase(prismaGroupeInfosRepository, code, legislature),
    ["groupe-infos", code, legislatureParam]
);
return resultToResponse(result);
```

| Résultat du use-case | Mis en cache ? |
|---|---|
| `ok(...)` | oui |
| `err("NOT_FOUND")` (erreur métier, stable jusqu'au prochain import) | oui |
| `err("DB_ERROR")` (panne technique) | **non** : la requête suivante réessaie |

Mécanisme : un `DB_ERROR` est levé à l'intérieur de `unstable_cache`, qui ne met pas en cache une fonction qui lève, puis reconverti en `Result` à l'extérieur.

`resultToResponse` n'ajoute l'en-tête `Cache-Control` (via `cachedJson`) qu'aux réponses de succès.

## TTL : configuration centralisée

```ts
// app/_shared/cache/cache.config.ts
export const CACHE_TTL_SECONDS = {
    NO_CACHE: 0,
    DAY: 60 * 60 * 24,
    WEEK: 60 * 60 * 24 * 7,
} as const;

export const ACTIVE_CACHE_TTL_SECONDS: number = resolveCacheTtl({ nodeEnv, devPerfEnabled, devPerfCache });

export const PARLIAMENT_DATA_CACHE_TAG = "parliament-data";
```

`resolveCacheTtl` (testé) décide selon l'environnement :

| Environnement | TTL |
|---|---|
| Production (`next build` puis `next start` / Docker) | **1 jour** (`DAY`) |
| Dev (`npm run dev`), tests | pas de cache (`NO_CACHE`) |
| Outil de perf local (`NEXT_PUBLIC_DEV_PERF=true`) | `DEV_PERF_CACHE=true` force le cache, `=false` le coupe |

En production, le TTL n'est qu'un **filet de sécurité** : le cache est vidé à chaque import (voir plus bas). Si cet appel échoue, les données ont au pire un jour de retard (l'import tourne chaque jour à 5 h).

`unstable_cache` refuse `revalidate: 0` (il lève une exception). C'est pour ça que `cachedRead` contourne `unstable_cache` entièrement et appelle `fn()` en direct quand `ACTIVE_CACHE_TTL_SECONDS === NO_CACHE`, plutôt que de lui passer `0`.

### Clés de cache

Chaque route passe à `cachedResult` des `keyParts` complètes : un identifiant d'endpoint unique (premier élément) puis **tous** les paramètres qui font varier le résultat (uid / code, législature, date, filtres, page…). Une clé incomplète ferait servir à une requête le résultat d'une autre. Vérifié sur les 37 routes de lecture (#133) ; à respecter pour toute nouvelle route.

### Où vit le cache en production

Sur le disque du conteneur Docker du front (`.next/cache`, une seule instance) : conservé lors d'un redémarrage du conteneur, perdu à chaque déploiement (l'image est reconstruite). Le cache repart donc à vide après un déploiement — la première visite de chaque page relit la base.

## Invalidation après import : `POST /api/revalidate`

À la fin de l'import quotidien, deputydex-data (dernière étape d'`updateAll`) appelle `POST /api/revalidate`, qui exécute `revalidateTag(PARLIAMENT_DATA_CACHE_TAG, { expire: 0 })` : tout le cache « données parlementaires » est vidé, les nouvelles données apparaissent sans redéployer.

L'accès à cette route est réservé à l'import (`app/_shared/cache/revalidate.guard.ts`, testé). La procédure d'exploitation est documentée dans le dépôt de déploiement.

## Filtres et tri des tableaux : statiques, pas fournis par l'API

Contrairement à un contrat "l'API renvoie `rows` + `filterFields` + `sortOptions` calculés dynamiquement", dans ce codebase `filterFields`/`sortOptions` sont déclarés **statiquement** dans la `TableConfig` du registry front (`app/(ui)/component-library/template/sections/block-section/table-config.types.ts`) :

```ts
export type TableFilterConfig = {
    sortOptions: SortOption[] | undefined;
    filterFields: FilterField[] | undefined;
    applyMode: "auto" | "manual";
};
```

L'API (le `gatewayFn` de la section) ne renvoie que les **rows**. Les `enumValues` d'un filtre ne sont donc pas calculés dynamiquement par le backend selon la législature — s'il faut ce comportement un jour, c'est une évolution à faire, pas l'état actuel.

## Résumé

| Décision                               | État actuel |
|------------------------------------------|--------------|
| Où s'applique le cache                    | `unstable_cache` dans le Route Handler (`cachedRead`, ou `cachedResult` pour un use-case qui renvoie un `Result`), pas `fetch({ next })` côté gateway |
| Erreurs mises en cache                    | `cachedResult` : succès et `NOT_FOUND` oui, `DB_ERROR` jamais |
| TTL actif                                 | Production : 1 jour ; dev et tests : pas de cache (`resolveCacheTtl`) |
| Changer le TTL                            | Modifier `resolveCacheTtl` dans `cache.config.ts` |
| Invalidation par tag après import         | `POST /api/revalidate`, appelé par deputydex-data en fin d'import |
| Filtres / tri de tableau                  | Statiques, déclarés dans `TableConfig` (registry front) — pas fournis dynamiquement par l'API |
| Header `Cache-Control` sur les réponses   | `cachedJson` l'aligne sur `ACTIVE_CACHE_TTL_SECONDS`, utile si un CDN est devant l'app |
