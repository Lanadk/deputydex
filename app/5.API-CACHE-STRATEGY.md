# Stratégie API & Cache

## Le mécanisme réel : `unstable_cache` côté route handler

Les gateways front (`app/(ui)/gateways/**`) font des `fetch` simples, **sans** option `next: { revalidate }` ni `next: { tags }` — le cache ne se joue pas là.

Le cache est appliqué **côté serveur, dans le Route Handler**, via deux helpers dans `app/_shared/cache/` :

```ts
// app/_shared/cache/cached-response.ts
import { unstable_cache } from "next/cache";

export function cachedRead<T>(
    fn: () => Promise<T>,
    keyParts: string[],
    extraTags: string[] = []
): Promise<T> {
    if (ACTIVE_CACHE_TTL_SECONDS === CACHE_TTL_SECONDS.NO_CACHE) {
        return fn(); // pas de cache : appel direct
    }

    return unstable_cache(fn, keyParts, {
        revalidate: ACTIVE_CACHE_TTL_SECONDS,
        tags: [PARLIAMENT_DATA_CACHE_TAG, ...extraTags],
    })();
}

export function cachedJson<T>(data: T, status = 200): NextResponse {
    return NextResponse.json(data, {
        status,
        headers: {
            "Cache-Control": `public, s-maxage=${ACTIVE_CACHE_TTL_SECONDS}, stale-while-revalidate=86400`,
        },
    });
}
```

Pourquoi côté route et pas côté `fetch()` client : `fetch(url, { next: { revalidate } })` ne fonctionne que pour du fetch fait depuis un Server Component. Les gateways de ce projet sont appelées depuis des **composants client** — `unstable_cache` dans le Route Handler fonctionne quel que soit l'appelant.

`keyParts` doit inclure l'identifiant de l'endpoint + tous les paramètres qui font varier le résultat (id, code, législature...), sinon deux requêtes différentes partagent la même entrée de cache.

## TTL : configuration centralisée

```ts
// app/_shared/cache/cache.config.ts
export const CACHE_TTL_SECONDS = {
    NO_CACHE: 0,
    DAY: 60 * 60 * 24,
    WEEK: 60 * 60 * 24 * 7,
} as const;

export const ACTIVE_CACHE_TTL_SECONDS: number = CACHE_TTL_SECONDS.NO_CACHE;

export const PARLIAMENT_DATA_CACHE_TAG = "parliament-data";
```

**État actuel : `ACTIVE_CACHE_TTL_SECONDS = NO_CACHE` (0)** — le cache serveur est désactivé aujourd'hui, chaque requête retape Postgres. Passer à un cache hebdomadaire/quotidien, c'est changer cette seule constante vers `CACHE_TTL_SECONDS.WEEK` ou `.DAY` — aucune autre modification n'est nécessaire dans les routes.

`unstable_cache` refuse `revalidate: 0` (il lève une exception). C'est pour ça que `cachedRead` contourne `unstable_cache` entièrement et appelle `fn()` en direct quand `ACTIVE_CACHE_TTL_SECONDS === NO_CACHE`, plutôt que de lui passer `0`.

---

## Invalidation par tag — pas encore câblée

`PARLIAMENT_DATA_CACHE_TAG` existe et permettrait d'invalider tout le cache "données parlementaires" en un seul `revalidateTag(PARLIAMENT_DATA_CACHE_TAG)` après un import — **mais rien n'appelle `revalidateTag` aujourd'hui**. C'est une piste pour plus tard (invalidation immédiate après le job d'import externe), pas un mécanisme en place.

---

## Filtres et tri des tableaux : statiques, pas fournis par l'API

Contrairement à un contrat "l'API renvoie `rows` + `filterFields` + `sortOptions` calculés dynamiquement", dans ce codebase `filterFields`/`sortOptions` sont déclarés **statiquement** dans la `TableConfig` du registry front (`app/(ui)/component-library/template/sections/block-section/table-config.types.ts`) :

```ts
export type TableFilterConfig = {
    sortOptions: SortOption[] | undefined;
    filterFields: FilterField[] | undefined;
    applyMode: "auto" | "manual";
};
```

L'API (le `gatewayFn` de la section) ne renvoie que les **rows**. Les `enumValues` d'un filtre ne sont donc pas calculés dynamiquement par le backend selon la législature — s'il faut ce comportement un jour, c'est une évolution à faire, pas l'état actuel.

## Résumé

| Décision                               | État actuel |
|------------------------------------------|--------------|
| Où s'applique le cache                    | `unstable_cache` dans le Route Handler (`cachedRead`), pas `fetch({ next })` côté gateway |
| TTL actif                                 | `NO_CACHE` (0) — cache désactivé |
| Changer le TTL                            | Modifier `ACTIVE_CACHE_TTL_SECONDS` dans `cache.config.ts` |
| Invalidation par tag après import         | Tag défini (`PARLIAMENT_DATA_CACHE_TAG`), **pas encore appelé** nulle part |
| Filtres / tri de tableau                  | Statiques, déclarés dans `TableConfig` (registry front) — pas fournis dynamiquement par l'API |
| Header `Cache-Control` sur les réponses   | `cachedJson` l'aligne sur `ACTIVE_CACHE_TTL_SECONDS`, utile si un CDN est devant l'app |
