# Outil de perf local (`/dev/perf`)

Mesure, sur le poste du développeur, ce que coûte chaque page et chaque appel d'API : base de données (SQL), serveur, navigateur, rendu (Web Vitals), cache. Réservé au local : **rien n'est mesuré ni exposé en production**.

## Activer

Dans `.env.local` :

```
NEXT_PUBLIC_DEV_PERF=true
# Pour mesurer avec le cache serveur (TTL 1 jour, local uniquement) :
# DEV_PERF_CACHE=true
```

Redémarrer le serveur (`npm run dev`, ou `npm run build && npm run start`) : une variable `NEXT_PUBLIC_` est lue au démarrage / au build. Après avoir modifié l'outil lui-même, Turbopack (mode dev) peut continuer à servir l'ancienne version : redémarrer, et supprimer `.next/dev` si besoin.

L'entrée **Performances** apparaît dans le menu, à côté de « Lib component ».

### Sécurité

- Sans la variable (donc en production) : pas d'entrée de menu, `/dev/perf` et `/api/dev/perf*` répondent 404, aucun en-tête `Server-Timing`, Prisma n'est pas instrumenté.
- **Même avec la variable**, la page et son API ne répondent qu'aux requêtes faites depuis la machine elle-même (`dev-perf.guard.ts`) : hôte `localhost` / `127.0.0.1` / `::1`, et toutes les adresses de `X-Forwarded-For` / `X-Real-IP` locales. Derrière le reverse proxy de production, ces en-têtes portent l'IP du visiteur : 404, même avec un `Host` falsifié. C'est une défense en profondeur : la règle reste de **ne jamais définir la variable en production** (elle est figée au build).

## Utiliser

Ouvrir `/dev/perf` dans un onglet (actualisation toutes les 2 s, interrupteur « Direct ») et naviguer sur le site dans un autre. La page est découpée en onglets :

- **En direct** : un point par appel d'API, dans l'ordre (heure · requête) — durée vue du navigateur ≥ serveur ≥ base de données, mesurées sur le même appel — et la tendance (moyenne glissante sur 10 appels). Fenêtre 1 min / 5 min / tout (« tout » par défaut : les fenêtres glissantes se vident quand on cesse de naviguer), filtre sur une requête. Indicateurs et **distribution p25 / p50 / p75 / p90 / p95** sur la même sélection.
- **Requêtes API** : par requête (`groupe-cohesion`…) et par domaine, appels **sans cache** (moy. / p95, dont base de données, nombre de requêtes SQL) et **avec cache** séparés, **accélération** (« ×36 », « ×100+ »), **poids** moyen de la réponse, navigateur. **Points d'attention** : requêtes qui lancent au moins 5 requêtes SQL par appel (à regrouper ?) et réponses de plus de 100 Ko (pagination, champs inutiles ?). Cliquer une requête la suit dans « En direct ».
- **Pages & rendu** : une ligne par page (visites regroupées) — durée jusqu'à la dernière donnée, **appels simultanés au pic**, **attente moyenne** hors serveur (réseau + file d'attente du navigateur), première → dernière visite, cache. **Web Vitals** par page (p75 des visites, couleurs selon les seuils officiels : LCP, FCP, CLS, INP, TTFB). Cascade de la dernière visite.
- **Rendu des composants** : temps de rendu React de chaque bloc du moteur de sections (graphiques, tableaux, calendrier, hémicycle…), mesuré par `<Profiler>` (`DevPerfProfiler`, posé dans `BlockSectionRenderer`) : nombre de rendus, moy. / p95, **rendu le plus long**, montage, cumul, pages ; graphique par type de bloc (« chart:bar », « table »…). Un bloc est monté avant ses données (état de chargement) : son montage est presque gratuit, le vrai rendu est un rendu suivant — d'où le classement sur le rendu le plus long. Orange au-delà de 16 ms (plus d'une image à 60 images/s), rouge à partir de 50 ms (tâche longue). **React ne mesure qu'en mode dev** (durées gonflées) **ou dans un build de profilage** : `npm run build:profile && npm run start` (`next build --profile`) ; dans un build de prod ordinaire, l'onglet reste vide. Les pages construites à la main (liste des scrutins…) ne sont pas mesurées.
- **SQL** : requêtes SQL regroupées par texte, triées par **temps cumulé** (exécutions × durée), avec les requêtes d'API qui les lancent.
- **Comparaison** : voir plus bas.

Chaque réponse d'API porte aussi un en-tête `Server-Timing` (`total`, `db`, `cache`, `endpoint`), visible dans l'onglet Network du navigateur (Timing), même sans ouvrir la page.

### Mesurer le gain du cache

1. `DEV_PERF_CACHE=true` dans `.env.local`, redémarrer.
2. **Vider le cache serveur** (bouton) puis **Vider les mesures**.
3. Visiter une page (cache froid : le SQL s'exécute), puis y revenir (cache chaud).

Le bouton est nécessaire : le cache serveur de Next est conservé sur disque (`.next/cache`) d'une session à l'autre, **même après un nouveau build** (constaté). Il appelle `revalidateTag(PARLIAMENT_DATA_CACHE_TAG, { expire: 0 })` via `DELETE /api/dev/perf/cache`.

### Comparer « avant » / « après » une optimisation

1. Mesurer l'état « avant » (navigation, ou `npm run perf:bench`).
2. Onglet **Comparaison** : **Enregistrer les mesures actuelles comme référence** (gardée dans le navigateur, exportable en JSON), ou **Importer un fichier** (référence exportée, ou résultat de `perf:bench`).
3. Appliquer l'optimisation, **Vider les mesures**, mesurer de nouveau.
4. Les écarts p50 / p95 s'affichent par requête (serveur, navigateur) et par page — vert : plus rapide, rouge : plus lent, ±10 % : bruit de mesure.

### Bench reproductible : `npm run perf:bench`

Visite des pages plusieurs fois dans un Chrome / Edge sans interface, laisse l'instrumentation mesurer (appels, SQL, sections, Web Vitals) et écrit un JSON à importer dans « Comparaison » (dossier `perf-results/`, ignoré par git).

```
npm run perf:bench -- --base http://127.0.0.1:3000 --runs 3 --cold \
  --pages /,/groupes,/groupes/RN,/deputes/PA842001 --label "avant #133"
```

- `--cold` : vide le cache serveur avant le premier passage ; `--keep` : ne vide pas les mesures déjà en mémoire ; `--wait` : ms par page (8000 par défaut) ; `--browser` ou `PERF_BROWSER` : chemin du navigateur si non trouvé.
- De préférence contre un build de prod (`npm run build && npm run start`). Ne pas lancer de build dans le dossier d'un `npm run dev` en cours (il casse le serveur de dev) : utiliser un autre dossier (`git worktree`).
- INP n'est mesuré qu'après une interaction (clic) : absent d'un bench sans interaction.

## Lire les chiffres

- **Couleurs des durées** (tableaux, cascade) : orange de 100 à 200 ms, rouge au-delà de 200 ms (`app/(ui)/_shared/adapter/duration.adapter.ts`, tokens `--ui-warning` / `--ui-danger`). Web Vitals : seuils officiels (`web-vital.adapter.ts`). Les indicateurs du haut restent sans couleur.
- **Mode dev (`npm run dev`)** : durées de rendu faussées (compilation à la première visite, double montage des effets en mode strict, donc appels en double), Web Vitals pessimistes. Bon pour comparer avant / après dans les mêmes conditions, et pour le SQL (fiable).
- **Build de prod local (`npm run build && npm run start`)** : mesures sans ces biais ; c'est la référence.
- **Base de données** = temps pendant lequel au moins une requête SQL tourne pendant l'appel. Les repositories lancent souvent leurs requêtes en parallèle (`Promise.all`) : additionner leurs durées compterait plusieurs fois les mêmes millisecondes.
- **Navigateur** = durée complète du `fetch` ; **attente** = navigateur − serveur. Une attente qui grandit avec le nombre d'appels simultanés vient de la file d'attente du navigateur.
- Une réponse du cache mesure souvent moins d'1 ms : les durées sont affichées au dixième de ms sous 10 ms.
- Base locale : les durées SQL ne valent pour la prod que si la base locale a le même volume de données.
- Mesures en mémoire du serveur (2 000 dernières par catégorie, compteur en haut de la page), perdues au redémarrage.

## Comment c'est branché

Aucune route ni aucun repository n'est modifié :

| Où | Quoi |
|---|---|
| `app/_shared/cache/cached-response.ts` → `cachedResult` | ouvre la mesure autour du use-case, détecte une réponse du cache (use-case non exécuté) |
| `app/infrastructure/db/prisma/prisma.ts` | extension Prisma qui chronomètre chaque requête (dont `$queryRaw`) et la rattache à l'appel en cours (`AsyncLocalStorage`) |
| `app/_shared/result-pattern/result-to-response.ts` → `resultToResponse` | clôt la mesure : en-tête `Server-Timing`, poids de la réponse, enregistrement |
| `SectionBlockLoader` | chronomètre le `gatewayFn` de chaque section |
| `BlockSectionRenderer` → `DevPerfProfiler` | temps de rendu React de chaque bloc (`<Profiler>`) |
| `app/(ui)/_shared/dev-perf/` | navigateur : `fetch` vers `/api/`, Web Vitals (`useReportWebVitals`), envoi à `/api/dev/perf` |
| `app/_shared/dev-perf/dev-perf.aggregate.ts`, `dev-perf.baseline.ts` | tous les calculs de la page (fonctions pures, testées) |
| `app/(ui)/components/dev-perf/` | un composant par onglet ; la page `dev/perf` ne fait que les assembler |

Une « requête » est nommée par le premier élément des `keyParts` de `cachedResult` (ex. `groupe-cohesion`) ; son domaine par son préfixe (`groupe-` → `groupes`). Une nouvelle route qui passe par `cachedResult` est donc mesurée sans rien ajouter.

**Limite connue** : la mesure d'un appel relie `cachedResult` et `resultToResponse` par l'objet `Result` renvoyé. Une route qui transformerait ce résultat entre les deux (au lieu de le passer tel quel) ne serait pas mesurée — aucune ne le fait aujourd'hui.
