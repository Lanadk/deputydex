# Outil de perf local (`/dev/perf`)

Mesure, sur le poste du développeur, ce que coûte chaque page et chaque appel d'API : base de données (SQL), serveur, navigateur, cache. Réservé au local : **rien n'est mesuré ni exposé en production**.

## Activer

Dans `.env.local` :

```
NEXT_PUBLIC_DEV_PERF=true
# Pour mesurer avec le cache serveur (TTL 1 jour, local uniquement) :
# DEV_PERF_CACHE=true
```

Redémarrer le serveur (`npm run dev`, ou `npm run build && npm run start`) : une variable `NEXT_PUBLIC_` est lue au démarrage / au build.

L'entrée **Performances** apparaît dans le menu, à côté de « Lib component ». Sans la variable : pas d'entrée de menu, `/dev/perf` et `/api/dev/perf` répondent 404, aucun en-tête `Server-Timing`, Prisma n'est pas instrumenté.

## Utiliser

Ouvrir `/dev/perf` dans un onglet (actualisation toutes les 2 s, interrupteur « Direct ») et naviguer sur le site dans un autre :

- **En direct** : un point par appel, au fil du temps (0 = maintenant) — temps passé dans la base de données et durée vue du navigateur — avec leurs moyennes glissantes (10 derniers appels). Fenêtre 1 min / 5 min / tout, et filtre sur une requête. Les indicateurs (moyenne / p95 du serveur, de la base, du navigateur, part servie par le cache) portent sur la même fenêtre et la même requête.
- **Requêtes** : toutes les mesures regroupées par requête (`groupe-cohesion`…) et par domaine, appels **sans cache** (use-case et SQL exécutés : moy. / p95, dont base de données, nombre de requêtes SQL) et **avec cache** séparés, **accélération** (« ×36 » ; « ×100+ » pour une réponse du cache sous la milliseconde), navigateur. Cliquer une requête la suit dans la vue en direct.
- **Pages** : une ligne par page, toutes visites regroupées : durée jusqu'à la dernière donnée (moy. / p95), évolution de la première à la dernière visite, appels servis par le cache. Cliquer une page affiche la cascade de sa dernière visite (sections et appels API, avec leur temps SQL).
- **Requêtes SQL les plus coûteuses** : regroupées par texte, triées par **temps cumulé** (exécutions × durée), avec les requêtes d'API qui les lancent.

Chaque réponse d'API porte aussi un en-tête `Server-Timing` (`total`, `db`, `cache`, `endpoint`), visible dans l'onglet Network du navigateur (Timing), même sans ouvrir la page.

### Mesurer le gain du cache

1. `DEV_PERF_CACHE=true` dans `.env.local`, redémarrer.
2. **Vider le cache serveur** (bouton) puis **Vider les mesures**.
3. Visiter une page (cache froid : le SQL s'exécute), puis y revenir (cache chaud).

Le bouton est nécessaire : le cache serveur de Next est conservé sur disque (`.next/cache`) d'une session à l'autre, **même après un nouveau build** (constaté : des appels servis par le cache dès la première visite après un build). Il appelle `revalidateTag(PARLIAMENT_DATA_CACHE_TAG, { expire: 0 })` via `DELETE /api/dev/perf/cache`.

## Lire les chiffres

- **Couleurs des durées** (tableaux, cascade) : orange de 100 à 200 ms, rouge au-delà de 200 ms (`app/(ui)/_shared/adapter/duration.adapter.ts`, tokens `--ui-warning` / `--ui-danger`). Les indicateurs du haut restent sans couleur.

- **Mode dev (`npm run dev`)** : durées de rendu faussées (compilation à la première visite, double montage des effets en mode strict, donc appels en double). Bon pour comparer avant / après dans les mêmes conditions, et pour le SQL (fiable).
- **Build de prod local (`npm run build && npm run start`)** : mesures sans ces biais ; c'est la référence.
- **Base de données** = temps pendant lequel au moins une requête SQL tourne pendant l'appel. Les repositories lancent souvent leurs requêtes en parallèle (`Promise.all`) : additionner leurs durées compterait plusieurs fois les mêmes millisecondes.
- **Navigateur** = durée complète du `fetch` (réseau + attente + serveur). Un écart important avec le serveur, sur une page qui lance beaucoup d'appels en même temps, vient de la file d'attente du navigateur.
- Une réponse du cache mesure souvent moins d'1 ms : les durées sont affichées au dixième de ms sous 10 ms.
- Base locale : les durées SQL ne valent pour la prod que si la base locale a le même volume de données.
- Mesures en mémoire du serveur (2 000 dernières par catégorie, compteur en haut de la page), perdues au redémarrage. La vue en direct montre « Tout » par défaut : les fenêtres 1 min / 5 min glissent avec le temps, et se vident donc quand on cesse de naviguer.

## Comment c'est branché

Aucune route ni aucun repository n'est modifié :

| Où | Quoi |
|---|---|
| `app/_shared/cache/cached-response.ts` → `cachedResult` | ouvre la mesure autour du use-case, détecte une réponse du cache (use-case non exécuté) |
| `app/infrastructure/db/prisma/prisma.ts` | extension Prisma qui chronomètre chaque requête (dont `$queryRaw`) et la rattache à l'appel en cours (`AsyncLocalStorage`) |
| `app/_shared/result-pattern/result-to-response.ts` → `resultToResponse` | clôt la mesure : en-tête `Server-Timing`, enregistrement |
| `SectionBlockLoader` | chronomètre le `gatewayFn` de chaque section |
| `app/(ui)/_shared/dev-perf/dev-perf.client.ts` | chronomètre les `fetch` vers `/api/`, envoie les mesures du navigateur à `/api/dev/perf` |
| `app/_shared/dev-perf/dev-perf.aggregate.ts` | tous les calculs de la page (fonctions pures, testées) |

Une « requête » est nommée par le premier élément des `keyParts` de `cachedResult` (ex. `groupe-cohesion`) ; son domaine par son préfixe (`groupe-` → `groupes`). Une nouvelle route qui passe par `cachedResult` est donc mesurée sans rien ajouter.
