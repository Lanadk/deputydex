# 📚 Component Library — Atomic Design côté client

## 🎯 Pourquoi une component-library interne ?

Le projet n'utilise pas de librairie de composants externe pré-stylée. À la place,
`app/(ui)/component-library/` est notre propre design system, construit au fur et à mesure des besoins de
l'app.

Objectifs :

- un seul endroit où vivent les briques UI réutilisables (pas de bouton redéfini 5 fois dans 5 pages)
- un vocabulaire commun (atoms / molecules / template) pour savoir où ranger un nouveau composant
- une doc vivante et testable : chaque composant a sa propre page de démo, avec preview + code affiché
- garder les pages métier (`app/(ui)/(views)/...`) concentrées sur la donnée, pas sur le style (à juste mesure ^^')

---

## 🧭 Comment la parcourir

En local (`npm run dev`), la route [`/component-library`](/component-library) liste tous les composants,
regroupés par catégorie (Atoms / Molecules / Templates). Chaque carte mène vers une page de démo qui montre :

- un aperçu visuel du composant, dans ses différentes variantes
- le code correspondant, affiché via un bouton *"Show Code"* (composant `CodeBlockLib`)

**Cette route est bloquée en production** — un `notFound()` serveur dans
`app/(ui)/component-library/layout.tsx` la désactive dès que `NODE_ENV === "production"`. C'est un outil de
dev, pas une page publique. Le lien "Lib component" n'apparaît d'ailleurs dans la sidebar (`nave-items.ts`)
que hors production, pour la même raison.

## 🧱 Le principe de l'atomic design (tel qu'on l'applique)

On s'inspire de l'atomic design (Brad Frost) sans en reprendre les 5 niveaux à la lettre — c'est de
l'atomic design à notre sauce, pas une implémentation stricte. Concrètement : pas d'*Organisms* (trop
lourd à maintenir pour la taille du projet) ni de niveau *Pages* dédié — les pages elles-mêmes vivent dans
`app/(ui)/(views)/`, en dehors de la component-library. Seuls deux niveaux de composition sont gardés, plus
un niveau structurel qui n'a pas d'équivalent direct chez Brad Frost :

```txt
app/(ui)/component-library/
  atoms/            # briques élémentaires, non composées
  molecules/        # compositions d'atoms (ou de plusieurs comportements)
  template/          # layout de page, sections, headers — structure, pas des "composants UI" au sens strict
  external/          # composants tiers isolés (ex. effets visuels) qu'on ne veut pas mélanger au reste
  types/             # types partagés à toute la lib (ex. IconLibType)
```

### Atoms

Un atom fait **une seule chose** et ne compose pas d'autre composant de la lib. Règle pratique : **1 à 2
tags HTML maximum** à l'intérieur (un `<span>`, un `<button>`...). Dès qu'un composant assemble plusieurs
comportements ou plusieurs atoms ensemble (un bouton + une popover, un input + son label + son état
d'erreur...), ce n'est plus un atom, c'est une molecule.

Exemples actuels : `Button`, `Span`, `Badge`, `Badge-avatar`.

### Molecules

Une molecule compose des atoms (ou gère un état/comportement plus riche : ouverture/fermeture, données
asynchrones, formatage...). C'est le niveau où vit la majorité des composants un peu utiles :
`ToggleSwitch`, `Input`, `Select`, `Table`, `Charts`, `FilterBar`, `ActivityCalendar`, `Cards`...

### Template

⚠️ À ne pas confondre avec le niveau *Templates* de Brad Frost (chez lui, un Template est encore une
composition de composants, avec du contenu placeholder). Ici, `template/` est une réalité propre au projet :
layout de page (`base-layout`), en-têtes de page (`headers/page-header`), zone de contenu (`page-content`),
et le moteur de sections config-driven (`sections/block-section`, voir
[`4.CONFIG-DRIVEN_client_side.md`](./4.CONFIG-DRIVEN_client_side.md)). Ce sont des briques de structure de
page, pas des widgets UI qu'on pose n'importe où.

## 🛠️ Créer un nouveau composant et le rendre visible à tous

Un composant qui n'existe que dans son propre dossier, sans démo ni entrée dans l'index, est un composant
que personne ne redécouvrira. La convention du projet est donc systématique :

1. **Choisir le bon niveau** — atom si le composant ne compose rien, molecule sinon (voir plus haut).

2. **Créer le dossier** `component-library/<atoms|molecules>/<mon-composant>/` avec :
   - `mon-composant-lib.tsx` — le composant, exporté en `PascalCase` suffixé `Lib` (ex. `BadgeLib`,
     `ToggleSwitchLib`). Props documentées avec des commentaires JSDoc au-dessus de chaque champ.
   - `mon-composant-lib.constants.tsx` — les données de démo : une fonction `getXSections()` qui retourne un
     tableau `{ title, code, component }`, un exemple par variante/cas d'usage significatif (voir
     `badge-lib.constants.tsx` pour un exemple court).
   - `page.tsx` — la page de démo elle-même : `PageHeaderLib` + `PageContentLib`, qui mappe les sections de
     `getXSections()` dans des `ComponentSectionCodeBlockLib`.
   - `mon-composant-lib.test.tsx` — tests unitaires si le composant a de la logique (état, calcul...).

3. **Enregistrer le composant dans l'index** : ajouter une entrée `{ name, path }` dans le tableau
   `Atoms` ou `Molecules` de `app/(ui)/component-library/page.tsx`. Sans cette ligne, la page de démo existe
   mais reste invisible depuis `/component-library` — donc invisible pour le reste de l'équipe.

4. **Styliser via `globals.css`**, pas en inline arbitraire : les classes utilitaires (`bg-surface-1`,
   `text-accent`, `border-main`...) et les blocs de composants (`.chart-lib`, `.sidebar-link`...) vivent
   dans `app/globals.css`, sous `@layer utilities` / `@layer components`. Un inline `style` reste acceptable
   pour une valeur réellement dynamique (une couleur calculée, une hauteur dépendant d'une prop), pas pour
   du style statique.

Ce pattern démo (`constants.tsx` + `page.tsx`, config statique mappée en JSX) est **local à la
component-library** — il sert à documenter un composant, pas à construire une page métier. Pour une page
métier construite depuis de la config (données récupérées au chargement, sections dynamiques), c'est le
moteur config-driven décrit dans [`4.CONFIG-DRIVEN_client_side.md`](./4.CONFIG-DRIVEN_client_side.md) qu'il
faut utiliser, pas ce pattern-ci.

---

## Règles simples à retenir

1. Si ça ne compose rien : atom. Si ça compose des atoms ou porte un comportement : molecule.
2. Pas de nouveau composant sans démo (`constants.tsx` + `page.tsx`) ni entrée dans `component-library/page.tsx`.
3. Le style vit dans `globals.css`, pas éparpillé en `style={{ ... }}` sauf valeur réellement dynamique.
4. `/component-library` est un outil de dev, désactivé en prod — n'y mets rien qui doive être vu par un
   visiteur du site.
